# Подготовка к публичному выпуску

Исходная точка аудита — 059acab. В solution есть WPF-клиент, библиотека, сервер активации и тесты. Серверный анализ доступен локально. Для публичного выпуска нужны проверенная эксплуатация, сверка расходов с AI Tunnel и подписанный установщик.

## Что подтверждается кодом

- Клиент с активированной лицензией отправляет кадры на сервер продукта. Прямой HTTPS-режим доступен с личным ключом, если лицензия ещё не активирована. Ключ этого endpoint хранится в Windows DPAPI на уровне пользователя. Это подходит для личного ключа. Общий ключ продукта должен жить на сервере.
- Локальный HTTP-тест подтверждает выдачу, активацию, отклонение повторной активации, сохранение после перезапуска и отзыв. В настройках Windows-клиента доступна активация. HTTP-тест проверяет сетевой клиент на локальном сервере. Окно активации и реальный TPM требуют ручной проверки. Локальный счётчик запросов не подтверждает расход провайдера.
- HTTP-тест запускает Kestrel, активирует лицензию сетевым клиентом, отправляет подписанную серию, проверяет структуру запроса к подменному провайдеру, однократное списание и отказ по общему лимиту. Живой захват Windows, TPM, внешний HTTPS и AI Tunnel требуют отдельной проверки.
- CI собирает solution, запускает тесты и после них публикует самодостаточную сборку Windows x64 в Artifacts. Команда публикации проверена локально. Запуск обновлённого workflow, установщик, подпись, обновление и удаление на чистой Windows ещё предстоит проверить.
- Кадры покидают компьютер при анализе. Для публичной сборки требуется явное описание получателя данных, условий захвата, хранения и удаления. Логи клиента сейчас записывают тип ошибки, а не полный текст исключения.

## Требования перед пилотом

1. **Активация.** Оператор вручную выдаёт уникальный случайный код. Сервер хранит хеш кода и состояние лицензии. Клиент создаёт ключ устройства при установке. Сервер регистрирует открытый ключ и проверяет владение закрытым ключом. Аппаратное хранилище Windows использовать при доступности. Замена устройства требует управляемого перевыпуска и отзыва старой привязки. Отдельно проверить, что скопированный код не активируется повторно и отозванная лицензия перестаёт выполнять запросы.
2. **Сервер.** Клиент идёт на HTTPS API продукта. Сервер проверяет лицензию, ограничивает размер кадров и число запросов, разрешает только утверждённые модели, отправляет данные фиксированному провайдеру и хранит его секрет отдельно. Понадобятся изоляция пользователей, отдельные права оператора, журнал выдачи и отзыва, резервная копия с проверкой восстановления.
3. **Баланс.** Оператор назначает тестовый лимит. Сервер резервирует верхнюю стоимость до вызова, проводит фактический расход по идентификатору операции и возвращает остаток резерва. Повтор с тем же идентификатором не списывает дважды. Параллельные запросы не расходуют один остаток. Для неясного исхода хранится статус сверки и блокируется автоматический повтор до выяснения результата.
4. **Экономика.** Замерить стоимость одного кадра и серии для выбранных моделей, включая оплачиваемые повторы и сбои. Себестоимость сессии включает расходы модели, долю инфраструктуры и поддержку. Для пилота нужны дневной лимит аккаунта и общий бюджет сервера. Розничную цену определять после замеров и проверки платёжного сценария.
5. **Проверка безопасности.** Проверить активацию, отзыв, доступ двух пользователей к чужим данным, повтор запросов, параллельный расход, ограничения входных данных и отсутствие ключей, кадров и ответов в логах. Проверить клиентскую сборку, зависимости и секреты в истории артефактов. Подготовить процедуру ротации ключа и остановки запросов к провайдеру.
6. **Windows.** Подготовить подписанный установщик и прогнать установку, обновление и удаление. Проверить первый запуск, выбор источника, потерю источника, отмену серии кадров, возобновление периодического анализа, масштабирование и доступность хоткеев. Публичный выпуск требует прохождения этого сценария на чистой Windows.

Первый интеграционный результат — оператор выдаёт лицензию и лимит, клиент активируется, выполняет один запрос через сервер, видит остаток, а повтор с тем же идентификатором не списывает повторно. Проверку начать с подменного провайдера, затем повторить со штатным провайдером на выделенном тестовом лимите.


## Сборка MSIX

Команда использует подготовленную папку самодостаточной Windows x64 сборки и Windows SDK с MakeAppx.

```powershell
pwsh -File scripts/Build-WindowsPackage.ps1 -PublishedDirectory ./publish/windows-x64 -OutputPath ./publish/ScreenAssistant-x64-unsigned.msix -Version 0.1.0.0
```

Для выпуска укажите `-Publisher` с точным Subject сертификата, `-CertificateThumbprint` сертификата из хранилища текущего пользователя и адрес сервера меток времени через `-TimestampUrl`. Зафиксируйте идентификатор издателя до первого выпуска и увеличивайте числовую версию при обновлении. Проверку установки проводить на чистой VM, которая доверяет издателю. На ней же проверить запуск из «Пуска», лицензию после обновления и удаление через настройки Windows.

Проверка подписи проведена локально на отдельном самоподписанном сертификате. SignTool сформировал подпись MSIX, криптографическая проверка CMS прошла. Доверие на этой машине не добавлялось. Для продолжения нужна чистая Windows VM и сертификат тестового издателя, которому доверяет только эта VM.
